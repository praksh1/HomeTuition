**Written for somebody arriving cold.** A human joining the project, or a second AI being asked
to help alongside the first. It assumes no prior conversation and nothing carried over from a
chat.

Everything here is read from the code as it stands on **26 August 2026**, not from memory.
Where a claim could not be verified, it says so. Where the owner has decided something, it is
marked as a decision rather than an opinion, and it should not be re-argued.

## 1. What the product is

A **live teaching platform for Nepal**.

A teacher schedules a class. A student finds it, books it, pays for it, and at the appointed
time joins a video call with a **shared whiteboard**. It runs on the web, on iOS and on
Android, from one codebase.

**The whiteboard is the product.** It is not a feature next to the video — it is the reason
somebody would choose this over a free video call. Treat it accordingly.

Anyone can teach any subject. In the founder's words a teacher might be *"a 15 year old or an
80 year old"*, and many will not own a laptop.

**Design target: a cheap Android phone on a poor connection.** Not a developer's laptop. This
has already caught real bugs — custom toolbar buttons once pushed Excalidraw's Selection tool
off the left edge of an iPhone screen, and the board looked perfect on a laptop while being
unusable on a phone.

### The name

The app is called **Sikshya**, everywhere a user can see — the interface and `app.json`. It
used to answer to "Guru" wherever the machine looked rather than the user (the browser tab,
the label under the icon when a student adds the site to an Android home screen). That is
fixed.

`HomeTuition` remains the name of the **repository** and the **Cloudflare Worker**. That is
plumbing nobody reads. Don't "fix" it.

The owner expects to rename once more before launch — *"probably GharTuition or TuitionGhar or
something similar"*. See section 9 for why the order of that matters.

## 2. What the owner is building toward

Gathered from decisions actually made, not from a mission statement.

- **A teacher with a phone and no equipment can run a real class.** Every design decision bends
  toward the person on the weaker device.
- **A student always knows where their money stands.** No state between "not booked" and
  "booked and paid". No refund that is agreed and then invisible. No promise the app cannot
  keep.
- **The platform can answer questions about itself.** Who was in that class? For how long? What
  did the teacher actually deliver? Every refund rule is a question about presence, and the app
  could once answer none of them. That is why attendance, activity logging and the ticket
  lifecycle exist.
- **Nepal-first, not Nepal-adapted.** Bikram Sambat dates, the festival calendar, eSewa and
  Khalti, connections that drop.
- **Costs stay small enough to survive.** The subscription is NPR 6,500; anything that costs
  more per teacher than that is not a business. This is why video provider cost is currently
  under review (section 7).

## 3. How to work on this project

### The owner is non-technical

The app was originally generated by Replit AI and has been substantially rewritten since. The
owner directs the product and does not read code. Practical consequences:

- **Explain why something broke and what it means for users**, not only what changed.
- **Never hand over a command without saying which directory to run it in.** This has caused
  real frustration.
- **Hand over the route, not the destination.** "You can change that in your settings", or a
  link to a documentation page, is not an instruction. Give the literal clicks: which site,
  which control, what it is called, what to type, what to expect afterwards. The owner's words:
  *"one little hurdle and I get stuck for minutes and hours."* If the exact path is not known,
  go and find it before saying anything.
- **Verify before claiming.** "It should work now" without evidence is not acceptable here.
  Several past bugs were declared fixed and were not, and the owner caught them.
- **When something cannot be done, say so plainly** with the honest cost, rather than
  half-building it.

### The owner develops on Windows

Every one of these has cost real time:

- The repo root is a **nested folder of the same name**: `C:\Projects\Paathshala\Paathshala`.
  Running from the parent gives `ERR_PNPM_NO_PKG_MANIFEST`. Always give the full path.
- **PowerShell blocks `.ps1` scripts**, and Node ships its tools as PowerShell scripts. So
  `pnpm`, `npx` and `npm` all fail with `UnauthorizedAccess`. **Always hand over `pnpm.cmd`,
  `npx.cmd`, `npm.cmd`.**
- On the owner's Windows copy, **`origin` points at an old abandoned repository**. Work goes to
  the `hometuition` remote. Run `git remote -v` before pushing. A fresh clone has one correct
  `origin`.
- `android/local.properties` needs **forward slashes** — it is a Java properties file, so
  backslashes are escapes.

### Security constraints, non-negotiable

- **Never ask for or accept a secret in chat.** Not `DATABASE_URL`, not `SESSION_SECRET`, not
  an API key. Hand over the *variable name* and let the owner set the value. The Daily.co API
  key was once pasted into a transcript and had to be rotated.
- **Students must never join a class without paying.** Invitations must not become free links.
- **There is deliberately no way to become an agent through the app.** An agent account is made
  by promoting a registered account directly in the database. `ISSUES.md` explains how and why.
- **An agent never sees or sets a password** — only issues a one-time code. Only the hash is
  stored, and it is never written to the audit log.

## 4. Architecture

pnpm workspaces monorepo. **Node 22+, pnpm 11.**

```
artifacts/api-server/   Express 5 + Drizzle ORM + WebSocket hub    → Railway
artifacts/sikshya/      Expo SDK 54 / React Native 0.81
                        / expo-router 6                            → Cloudflare Workers
lib/db/                 Drizzle schema, shared                     → Neon Postgres
scripts/                seeding and shared tooling
```

Web, iOS and Android build **from one codebase**. Metro resolves `.web.tsx` before `.tsx`,
which is how platform-specific implementations are split — see `DailyEmbed` and `SmartBoard`.

**Video** is Daily.co: the Prebuilt iframe on web, the native SDK on iOS/Android. Teachers get
an owner token so they can moderate.

**Two WebSockets, deliberately separate:**

| | |
|---|---|
| `ws/classroomHub.ts` | Presence, in-class chat, session status, the whiteboard. Per class. |
| `ws/userHub.ts` | Notifications: messages, new followers, classes going live. One per signed-in app. |

**Board state is held in memory.** A server restart loses a live board. That is a known gap.

**The whiteboard is Excalidraw**, running as the deployed web board inside a WebView on phones.
The consequence is useful: *a board feature that works on the web already works on phones.*
What breaks one is handing it a device-local `file://` path instead of the file's bytes.

### Live addresses

| | |
|---|---|
| Site | `https://hometuition.praksh-dhakal.workers.dev` |
| API | `https://workspaceapi-server-production-5a63.up.railway.app` |
| Database | Neon Postgres |
| Files | Cloudflare R2 |

**Production release state (2026-08-29):** The site was explicitly deployed from branch
`claude/excalidraw-whiteboard-sync-gjoqaz` at commit `13c4d3a`. It includes the approved teacher
and student classroom call-window redesign (Hidden/Small/Medium/Full), the preceding edge-to-edge
classroom and chat work, and all other frontend changes already committed on that branch. Daily
remains active. Full build/deployment evidence and the deliberately untouched areas are in
`.agents/worklog/2026-08-29-codex-production-release.md`.

### The two rules that must not be broken

**1. Access control lives in one place.** `artifacts/api-server/src/lib/membership.ts` answers
"may this user be in this class?" and **both doors** — the video room route and the WebSocket —
call it. They used to disagree: the socket checked membership while the room route only checked
you were logged in, so an unenrolled student saw a "not enrolled" banner with the teacher's
video playing behind it. **Never re-implement this check somewhere else.**

**2. Booking is atomic, and there is no "pending" payment.** `POST /sessions/:id/book` runs one
transaction that either commits an enrolment already marked paid, or writes nothing at all. The
old two-step flow left students holding classes they believed they had bought but could not
enter. **Do not reintroduce a state between "not booked" and "booked and paid".**

### Deployment

- **The API redeploys itself** when you push — Railway watches the repo.
- **The web app deploys itself too**, via `.github/workflows/deploy-web.yml`. A push to `main`
  runs the checks and deploys. It needs `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` as
  repository secrets; without them everything is still checked and the deploy step says so
  rather than failing.
- Manual path, if the workflow is ever unavailable:
  `pnpm --filter @workspace/sikshya run build` then `npx wrangler deploy`.

**`EXPO_PUBLIC_API_URL` is baked in at build time, not read at run time.** Metro used to cache
that substitution without the value in its cache key, so changing the API address and
rebuilding succeeded while still shipping the old one. `scripts/build.js` now clears the
bundler cache when the address changes and fails the build if the result does not contain it.

### Running it locally

From the repo root:

```
pnpm run dev:api      # port 8080
pnpm run dev:app      # Expo web, port 8081
pnpm run typecheck    # all four packages — run before claiming anything works
pnpm run db:push
pnpm run seed
```

**Secrets are not in the repo.** `.env` at the root holds `DATABASE_URL`, `SESSION_SECRET`,
`PORT`, `NODE_ENV`; `artifacts/sikshya/.env` holds the app's. Both are gitignored. A fresh
clone will not run until they exist — ask the owner rather than guessing.

## 5. Money — packages, pricing, and what actually happens today

**Read this section before proposing anything about pricing.** The rules are more considered
than they look, and several were decided after an argument that should not be repeated.

### The headline

**No money moves yet.** Payments run in **gateway** mode when a provider is configured and
**simulated** mode when none is. The mode follows from what exists in the environment rather
than from a flag — configuring a real provider permanently disables simulated mode, so real
payments cannot be switched on while the free door is still open. That self-tightening is
deliberate. See `lib/payments.ts`.

**Warning, and this one bites:** setting `PAYMENT_WEBHOOK_SECRET`, `ESEWA_MERCHANT_ID` or
`KHALTI_SECRET_KEY` today will **decline every booking**, because the eSewa/Khalti branch is
not written. Do not set them until it is.

### Package A — the monthly tier (the main product)

A teacher pays Sikshya **NPR 6,500 a month** and gets **one recurring class**: same time every
day, up to **45 students**, up to **90 minutes**. Students pay the teacher a monthly fee,
pro-rated if they join part-way through.

Constants, all in `artifacts/api-server/src/lib/monthly.ts`:

| Constant | Value | Meaning |
|---|---|---|
| `TEACHER_TIER_PRICE` | 6500 | What the teacher pays Sikshya, in rupees |
| `PLATFORM_SHARE` | 0.3 | Sikshya's cut of a **student's** fee |
| `MIN_SESSIONS_PER_CYCLE` | 25 | The delivery floor |
| `MAX_SESSIONS_PER_CYCLE` | 40 | Ceiling on a cycle |
| `MAX_MAKEUPS_PER_CYCLE` | 5 | Make-up classes allowed |
| `MAX_ABUSES_PER_CYCLE` | 5 | Black marks before suspension |
| `PLAN_AUTOSTART_DAYS` | 7 | Clock starts anyway if the class is never created |

**The teacher's 6,500 is entirely Sikshya's.** It is what they pay to run a class, not a share
of anything.

#### The one rule everything else follows

**A month here is thirty times twenty-four hours from a timestamp. It is never a calendar
month.**

This is the answer to "make sure the two date formats don't conflict". A Bikram Sambat month
runs 29–32 days and a Gregorian one 28–31. If any price were worked out from "a month", the
same class would cost two different amounts depending on which calendar somebody's phone was
set to. **No calendar arithmetic touches a price, anywhere.** Both calendars are display only,
converted at the moment something is shown to a human.

#### Teacher and student can never be in different months

There is **one clock**. The teacher's cycle *is* the student's cycle. A student joining on day
twelve pays for what is left of the teacher's month and then renews on the same day the teacher
does. The alternative — each student on their own month — is what creates the problem in the
first place.

| Situation | What happens |
|---|---|
| Student joins on the last afternoon | Pays for the one class left, not a month |
| Student joins with no classes left | Refused, told when the next month starts, charged nothing |
| Student joins on day 12 | Pays 18/30, renews with everybody on day 30 |
| Teacher's month rolls over | Every student rolls over at the same instant |
| Teacher stops mid-month | Every student is owed for the classes that will not happen |

The clock starts when the teacher **creates the recurring class**, not when they buy — a plan
bought and never used would otherwise sit forever having bought nothing, so after seven days it
starts anyway.

#### Pro-rating

Pro-rated **by classes, never by days** — what is sold is classes, and the quality floor is
stated in classes, so pricing in days would mean two units and an argument in the gap. The
denominator is **frozen when a student joins**. Part-rupees **round down, in the student's
favour**.

#### Two ways to be owed a refund — either is enough

1. **The teacher missed the floor** — fewer than 25 classes held. The *whole* shortfall comes
   back, not merely the part beneath 25: missing the floor voids the month's promise rather
   than discounting it.
2. **You got less than your share.** 25 of 30 is a promise to hold five sixths, so a student is
   owed when what they received falls below five sixths of what they *bought*. Someone who
   joined with 9 classes left and received 6 is owed for 3, even though the teacher held 27
   across the month and cleared the flat floor.

Rule 2 was added after the owner agreed rule 1 alone was too harsh on a late joiner. It is
*added*, not substituted — the flat floor still protects somebody rule 2 would miss. For a
student who bought the whole month, rule 2 reduces to exactly "25 of 30", so the original rule
is untouched for the case it was written about.

**Stopping early is judged differently, on purpose.** A teacher suspended on day 28 has usually
held exactly 25 — the floor — but their students have days left that will now never happen, so
they are owed for them.

**Money comes out of the teacher's share first, then Sikshya's fee, never the student's.** That
ordering only means anything because the money is **held**: a student's fee is not paid out
when they join, it sits until the month has been delivered.

#### Missing a class

A missed class is **not** an immediate black mark. The teacher has 48 hours to put a make-up on
the calendar, and one arranged — even late — clears the mark. Black marks are **counted from
the ledger, never stored**, so what a teacher is shown and what they are judged on cannot
drift. At **3** they are warned in the strongest terms the app has. At **5** the class is
suspended for 30 days, everyone is refunded for the rest of the month, and the class ends.
Suspension **is** recorded, unlike the marks.

The teacher chooses a make-up's date and time. It may be any future instant inside the same
30-day cycle; it cannot overlap another class, land during declared leave, replace a miss from
an older cycle, or cross the cycle boundary. Five are allowed per cycle. A make-up contributes
to the 25-class floor only after its session was actually held — putting it on the calendar is
not delivery.

Held or missed is read from `sessions.startedAt`, **never from anything the teacher confirms**.

### Package B — pay-per-class (regular sessions)

A teacher creates a one-off class and sets its price (`sessions.price`, whole rupees). A
student books and pays for that class alone.

**Sikshya's revenue here is the teacher's subscription, not a cut of the booking.** A teacher
buys a monthly plan that entitles them to a number of sessions. `SUBSCRIPTION_TIERS` in
`artifacts/api-server/src/routes/teachers.ts`:

| Tier | Sessions / month | Price |
|---|---|---|
| `base` | 10 | NPR 2,000 |
| `tier1` | 15 | NPR 2,800 |
| `tier2` | 20 | NPR 3,500 |
| `tier3` | 25 | NPR 4,220 |
| `tier4` | 30 | NPR 4,700 |

Separate from the NPR 6,500 monthly recurring-class tier in Package A, which has its own table
(`teacher_plans`) and its own rules. A teacher could hold both. `POST /teachers/:id/subscribe`
sets the tier, `GET /subscription-tiers` publishes the list, and the chosen allowance is
written to `teacher_profiles.max_sessions_per_month`.

**The allowance is enforced** (`lib/tierLimits.ts`, the rules; `lib/sessionAllowance.ts`, the
query; refused at `POST /sessions` with a 402). Two rules worth knowing:

- **A "month" is thirty times twenty-four hours**, matching Package A. Never a calendar month —
  the reason is the same one, and is above.
- **The limit is "no more than N classes inside any thirty-day stretch."** Not a counter that
  resets on a date: that needs a stored anchor, and the only place for one is a new column on
  `teacher_profiles`, which is the deploy-window trap. Counting off the classes themselves needs
  no schema change, cannot drift from what actually happened, and cannot be gamed by stacking
  classes either side of a boundary.

Behaviour that follows: **days of a monthly recurring class do not count** (they are ordinary
`sessions` rows, so a naive count would bill a teacher for classes they paid NPR 6,500 for);
**a cancelled class frees its slot**; and a refusal offers an upgrade only when that upgrade
would actually take the class.

**One thing here is still unfinished.** The subscription is **not really charged**.
`POST /teachers/:id/subscribe` now goes through `chargeForMonthly` — the same gate every other
payment passes, so it approves in simulated mode and refuses in gateway mode rather than
silently taking real money through an untested path. But no money moves and, unlike a refund,
nothing records that a teacher *owes* NPR 2,000. Finishing it is the payment-provider item on
the pre-launch list, not a separate job. See section 8.3.

#### Refund arithmetic

| Rule | Constant | Value |
|---|---|---|
| A class can only be moved more than N hours before it starts | `RESCHEDULE_LOCK_HOURS` | 48 |
| A moved class must be at least N hours away | `RESCHEDULE_MIN_NOTICE_HOURS` | 48 |
| A student can drop more than N hours before | `DROP_DEADLINE_HOURS` | 24 |
| Window to claim a refund after a schedule change | `SCHEDULE_CHANGE_REFUND_HOURS` | 24 |
| Student drops in time → they get back | `STUDENT_DROP_REFUND_SHARE` | 50% |
| …of the remainder, teacher keeps | `TEACHER_CANCELLATION_SHARE` | 25% |
| …and the platform keeps | `PLATFORM_CANCELLATION_SHARE` | 25% |

If the **teacher** moves it, cancels it, or an agent uses discretion: **the whole price goes
back** and nobody keeps a share. The three parts always add back to the price, and the student
is rounded **up** — a 50% split of an odd price puts its stray rupee with the person getting
the refund. `refundSplit` in `lib/sessionChanges.ts`, and there is a test that no arithmetic
can invent or lose a rupee at any price.

> **Note for anybody reading the booking transaction.** There is no commission recorded when a
> booking succeeds — `platformShare` appears in the refund path and nowhere in the booking
> path. That is **not** a gap: the platform's revenue on pay-per-class is the teacher's
> subscription above, not a cut of each booking. Do not "fix" it by adding a commission.

### Refunds are a debt, not a payment

A ticket can be resolved with "Refunded in full" and the reporter reads it, **but no money
moves.** The Refunds tab in the support desk *is* the payment system: every row is a debt
somebody settles by hand and records a reference against. Students are told a refund is
*requested* and takes 5–7 business days, which is true and stays true until a provider exists.
`REFUNDS.md` section 2b.

## 6. What is built

Verified as present in the codebase. "Tested" means there is a suite that exercises it; see
section 10.

### Accounts and access

- Registration, login, sessions, roles (student / teacher / agent).
- `lib/membership.ts` as the single access-control answer, called by both doors.
- Agent accounts made by promoting a row in the database — deliberately no in-app path.
- Password reset by one-time code issued by an agent, who never sees the result.
- Account suspension with a written reason.

### Booking and payment

- Atomic booking: one transaction, paid or nothing.
- Simulated / gateway payment mode inferred from the environment.
- Refund arithmetic for both tiers, with tests that money is never invented or lost.
- Refund queue an agent works.

### The classroom

- Daily.co video: Prebuilt iframe on web, native SDK on phones, teacher gets an owner token.
- **Excalidraw whiteboard** with object manipulation, an infinite canvas, shared images and
  PDFs as real board objects, and a scene that stays in step with every student — including
  erasures and the teacher's viewport.
- **Shape recognition** — a confident freehand stroke is replaced with a real shape in one
  undoable step; writing and uncertain strokes are left alone. 27 tests.
- In-class chat on web and native, unread counts.
- 5-minute early-join lobby.
- Attendance: who was in the class, when they arrived, how long they were connected, how much
  they drew.

### The clock a class runs on

**One timeline, in one file.** Doors open **10 minutes before** the booked start. A student's
Join greys out **5 minutes after** the booked finish. The call stops, and no teacher may
reopen it, **10 minutes after that**.

Measured from the **booked** slot, never from when the teacher pressed start — so a teacher
beginning twenty minutes late does not get twenty extra minutes. Deliberate: a student who
booked 10:00–11:00 needs to know they are free at 11:00.

`api-server/src/lib/sessionStart.ts` is the original; `sikshya/utils/sessionWindow.ts` is the
app's mirror. **A test reads one and compares the other**, because a mirror that drifts leaves
both halves looking correct in isolation.

### When a class ends or a teacher drops (newest work)

One behaviour, whichever way the teacher disappeared — pressing **End**, or their connection
dropping:

| Phase | Duration | What the student sees |
|---|---|---|
| Quiet | 5 min | Nothing changes; finish the thought, copy the board |
| Warned | 10 min | A banner: stay for ten more minutes, or leave now |
| Over | — | The call closes itself |

`sikshya/utils/aloneInCall.ts` (`QUIET_MS` 5 min, `NOTICE_MS` 10 min, `TOTAL_MS` 15 min) and
`hooks/useAloneInCall.ts`. The **video room is deliberately not torn down** when a class ends,
so a teacher who pressed End by accident can come back and the video resumes, inside the app's
existing three-hour rejoin window.

### The monthly tier

Every row in `MONTHLY.md` section "What is built": the arithmetic, local-time→instant
conversion, four tables plus a boot guard, seven routes, class-days materialising into ordinary
classes, changing the daily time with 18 hours' notice, make-ups and abuse counting and
suspension, closing a month and paying refunds, group chat with teacher-only pinning, and
homework set / handed in / marked / handed back.

**How a class-day becomes a class:** a day before it is due, each class-day becomes an ordinary
`sessions` row with every student that month enrolled and marked paid. Once the row exists the
class **is** an ordinary class, so the video room, the whiteboard, the chat and `membership.ts`
all work on it untouched. Which leaves one hole, and it is guarded: a materialised class-day
costs nothing, so `POST /sessions/:id/book` **refuses** it outright and those days are hidden
from Discover.

It runs as a **lazy sweep off reads**. There is no scheduler in this project.

### Messages and threads

Three distinct conversations, on purpose:

| | Lives | Purpose |
|---|---|---|
| **Messages** | Forever | Person to person. Conversation-style, newest first, drafts inline, attachments, reactions. |
| **Class thread** (`/session/:id`) | Outlives the class | Teacher + everyone who paid. For "I'm running late", and for evidence in a refund argued weeks later. |
| **In-class chat** | Memory only | Goes with the room when the lesson ends. |
| **Monthly portal thread** | The whole course | One conversation for a month of classes, not one per class-day. Teacher-only pins. |

The monthly thread opens on the **newest** message; the class thread opens on the **oldest**.
That is intentional — oldest-first is harmless for one lesson and precisely backwards for a
month.

### The class's own page — `/session/:id`

Who booked, before it runs. Who attended, after. A clock **taken from the server rather than
the handset**, because a phone whose clock is half an hour out would otherwise tell its owner
their teacher was late for a class that had not started.

### Support desk — `/(admin)`, reached at `/desk`

The ticket queue; one ticket with its class, attendance, thread and findings on one screen; and
the four things an agent can do — close a ticket with a written decision, suspend an account
with a reason, issue a password reset code, review teaching credentials.

`/desk` is a signpost rather than a second login — the same form, their own account, and the
app routes them by role.

**A request has a number and a life.** `HT-000123`, and a trail: Request Created → Opened →
Assigned → Being worked on → Resolved / Denied / Cancelled. Resolving or denying takes a
**written reason**; an agent may attach a supporting document; agents can write notes to each
other the reporter never sees. Every move is written to `ticket_events` **in the same
transaction** that changes the status, because a status that changed with nothing behind it is
what the owner was looking at when they said *"a user can create several hundred requests
without knowing the status of their requests"*.

Rules live in `api-server/src/lib/tickets.ts` — **forward-only**, and the desk draws its buttons
from them, so a button that would be refused is never shown. **Three requests per person per
rolling 24 hours**; a refused one writes nothing at all. To the reporter an agent is "Sikshya
Support".

### Everything else

- **Activity log** — everything anybody does that changes something, written by a *middleware*
  rather than by hand-written calls per route. A claim of "every action" that depends on
  somebody remembering is not one worth making.
- **Notifications** — real, over `ws/userHub.ts`, with per-user preferences stored server-side.
  What users saw before was six samples the app invented in local storage on first run.
- **Reviews** — written in the student's own words (the app used to invent them) and anonymous
  to everybody.
- **Teachers are told when somebody books**, which they never were.
- **File uploads** to Cloudflare R2, with per-feature access control.
- **`GET /admin/video-usage`** — participant-minutes for a month, plus estimated cost and
  egress at a rate the caller supplies. Nothing new is recorded for it; the attendance data
  already had the answer.

## 6b. The design system, and the visual upgrade

Agreed with the owner on 27 August 2026 and specified in full in **`DESIGN.md`**. The short
version:

- **Crimson `#C41E3A` is identity and a LIVE class. Nothing else, and never a button.** Every
  action a person takes — Join, Book & Pay, Start — is royal blue `#123C8C`. The two are the
  colours of the Nepali flag, used as ink and action rather than decoration.
- Before this, `primary` was crimson and `destructive` was red, so **the button that took a
  student's money and the button that cancelled their class were both red.**
- Destructive is a burnt rust `#9A3412`, chosen because the obvious `#B3261E` measures 13° in
  hue from the brand crimson — the same red to any human eye.
- Nine named type steps replace eighteen ad hoc font sizes. Money and clocks get tabular figures.
- **Dark mode is deliberately absent** — the owner's call, the product is a whiteboard. Do not
  add one without asking.

`constants/colors.ts` had been bypassed **468 times** by hex written straight into screens, so
`lint:design` runs in CI as a **ratchet**: a per-file baseline that may fall and may never rise.
It is at 223 hex / 429 sizes and dropping as screens are converted.

### The thing every converted screen has had in common

**Each one contained at least one number or claim with nothing behind it.** A dead column
written once at registration, a hardcoded array, a value derived from `?? 0`. A teacher's
dashboard reporting "NPR 0k earned" forever; a subscription screen showing three invented
payments and promising session recording that exists nowhere in the codebase; a storefront
labelling every teacher "Available" from a column no screen writes.

The full list, how to test for one, and what to do instead are in
`.agents/backlog/ui-upgrade-progress.md`. **Open every new screen expecting to find one.**

## 7. What is not built

In rough priority order. Nothing here is hidden or half-claimed.

**1. Email cannot be sent until a provider is configured.** `lib/mailer.ts` is written and the
preference switches exist. Without `RESEND_API_KEY` and `EMAIL_FROM` the app says so plainly
rather than pretending. Same self-describing pattern as payments.

**2. Board performance is measured but not on a real phone.** With the processor throttled to
roughly a budget Android's speed, a 500-element lesson paints in ~1.6 s and a new stroke lands
in ~140 ms — and it still paints at 25× slowdown. That says the code is not doing anything
foolish. It does **not** reproduce a weak GPU, memory pressure or thermal throttling.
`artifacts/sikshya/scripts/perf-tests` runs on every deploy.

**3. Shape recognition failed a real teacher test and is now queued for removal from the active
path.** A handwritten `A` and ordinary rough ink can be replaced with an unintended arrow or
shape. Preserve explicit Excalidraw shape tools, but disable automatic freehand conversion. The
owner's acceptance criteria are in
`.agents/backlog/2026-09-02-owner-corrections-and-stream-poc.md`, section 5.

**4. Handwriting-to-text is not built.** On-device OCR was tried and withdrawn: Tesseract reads
printed text, and on handwriting a clearly drawn "B" came back "L". Doing it properly needs ML
Kit (free, native only) or MyScript (paid). `WHITEBOARD.md` section 4 lays out the options
honestly.

**5. A large PDF over the WebView bridge is untested on a real phone.** A PDF picked on a phone
reaches the board — the app reads the file into bytes and posts those. But an 8 MB PDF is ~11
MB base64, and the biggest thing proven across that bridge is a ~1 MB photo. It fails loudly
rather than silently. `ISSUES.md` → E3.

**6. Board state is in memory.** A server restart loses a live board. Persisting it is a known
gap.

**7. No Bikram Sambat date picker.** Nepali users see Gregorian dates only. Note that this is a
*display* gap and must stay one — see the "one rule" in section 5.

**8. A refund that is agreed still has to be paid by a person.** Section 5, and `REFUNDS.md`
section 2b.

**9. The dispute workflow around a ticket does not exist.** The ticket has a lifecycle, a
number and a history. What is missing is the timetable the owner specified on top of it — three
days for the teacher to respond, two days to tell the student, the appeal. `REFUNDS.md` section
4.

**10. Marking drawn in the app has no drawing surface yet.** It is stored and handed back; a
teacher currently marks with words or by uploading a marked-up file.

**11. Video cost is under review.** Daily.co is billed per participant-minute. At the monthly
tier one teacher is roughly 37,440 participant-minutes a month; at a plausible rate that is
more than the NPR 6,500 subscription. **Nothing has been acted on and Daily.co is untouched.**
A provider seam already exists — `api-server/src/lib/video/types.ts`, two functions
(`ensureRoom`, `joinToken`), selected by the `VIDEO_PROVIDER` environment variable, with a test
that runs the whole server twice (on Daily and on a stub) and checks the rules come out
identical. `VIDEO.md`.

**12. The owner's 2026-09-02 correction packet is the next implementation queue.** It covers
operator/email wording, locking tiers before payment, a reported old reset link that worked,
temporary audited test-teacher access, disabling automatic shape conversion, fixing the
call-window minimize semantics, and a separate Stream Video proof of concept. Read
`.agents/backlog/2026-09-02-owner-corrections-and-stream-poc.md` before changing any of these.
The packet is specification only: none of those changes were implemented when this paragraph
was added.

## 8. What needs a decision — questions for the owner, not for an AI

**Do not start any of these without an answer.** They are pricing and fairness questions before
they are code questions. Full context is in `.agents/backlog/monthly-partial-months-and-dropping.md`,
written to be readable months later by somebody who has forgotten the conversation.

### 8.1 A month that is not a whole month

> *"In the month of Bhadra there are 17 days after which national holidays/festivals start and
> everyone goes on leave — can a teacher create sessions for only those 17 days?"*

This is not a setting. A monthly class runs **every day**, and three rules are built on that:
the price (pro-rata on sessions remaining), the delivery floor (25), and suspension. **A 17-day
month breaks all three** — 25 is not a floor a 17-day month can clear, so every teacher running
one is in permanent shortfall and suspended by a rule meant to catch neglect.

The floor has to stop being an absolute number and become a **proportion of the days the class
actually offers** — something like "at least 85% of the days you published". That single change
is what lets a class of any length exist.

The harder half: **Nepal's festival calendar is not fixed to Gregorian dates and moves year to
year, so the app cannot infer the days.** The teacher has to publish them — a calendar they
paint, not a rule the app guesses.

To settle first:
- Is the floor a percentage of published days, and what percentage?
- When a teacher publishes 17 days, is the monthly price the same as for 30? *(It should not
  be, but it is their revenue and their call.)*
- Does a student joining a 17-day cycle see "17 classes" everywhere, including the receipt?
- What happens at the boundary of a cycle that ends mid-festival?

### 8.2 Dropping the whole course mid-month

`stoppedEarlyRefund` pays back the part of the month the student has not used. The hole: **it
refunds days the student themselves chose not to attend.** A student can book a month, skip a
fortnight, drop out, and be refunded for the fortnight they skipped — while the teacher held
every one of those classes and was paid for none of them.

Refunding **unheld** days is obviously fair. Refunding **held days the student did not attend**
is obviously not. But attendance is a blunt instrument: a student who was ill, or whose
connection failed, looks identical to one who lost interest — and this platform is aimed at
people on cheap phones and poor connections where that failure is common.

A defensible middle: refund only the days **not yet held** at the moment of dropping, and say
so plainly **at the point of joining**. Simple, cannot be gamed either way, does not require
the app to judge why somebody was absent. It also means dropping on day 25 gets very little
back — which is correct, and has to be *visible before they pay*.

To settle first:
- Unheld days only, or something more generous?
- Is there a **cooling-off period** — say the first two days — where the whole amount comes
  back? *(Common, cheap, heads off most complaints.)*
- Does dropping bar re-joining the same class that cycle at the pro-rata price? Without a bar
  it is a way to dodge the shortfall rule.
- Does the teacher's delivery floor still count days a dropped student did not take?

### 8.3 Two open questions about the teacher tiers

The allowance is enforced and the self-approval hole is closed (section 5). Two product calls
were made without waiting for an answer, because the work would otherwise have stalled. Both
are cheap to change and both are the owner's to settle:

1. **The eleventh class on a ten-class plan is refused outright.** The alternative is to create
   it and prompt for an upgrade. Refusing mid-month means a teacher who cannot teach a class
   they may already have told students about; allowing it means a limit nobody respects. The
   refusal already names the upgrade that would take the class, so switching is small.
2. **A cancelled class frees its slot.** It was not taught, and the refund rules already make
   cancelling expensive. If teachers churn cancellations to dodge the limit, count them
   instead — nothing else changes.

And one thing genuinely unfinished: **nothing records that a teacher owes their subscription.**
Refunds write a debt row an agent works; subscriptions do not. It belongs with the
payment-provider work.

Full detail, including what was built and why, in
`.agents/backlog/teacher-tier-plans-not-enforced.md`.

### 8.4 The video provider

Which provider, and self-hosted or managed. The trade is roughly *cost* against *who gets woken
up when a class will not connect at 8pm in Kathmandu*. The owner is non-technical, which is the
strongest argument against self-hosting and has to be weighed honestly against the numbers.

### 8.5 Chat, once an installed app exists

**Daily's chat is web-only.** The moment an installed app is in someone's hands, a class mixing
an app user and a browser user has two conversations that cannot see each other, and both look
like they are working. Either bridge them, or keep Daily's chat off and rely on the app's own
panel. Currently Daily's chat is **disabled on purpose**; re-enabling it splits the class.

### 8.6 Infrastructure the owner asked about

- **Fewer services.** Today: Railway (API), Cloudflare (site + R2), Neon (database), Daily
  (video), GitHub. The owner logs into four or five things and expects to lose track. Whether
  consolidating is worth it needs measuring, not agreement.
- **An API gateway**, to make the app "faster and smoother". Whether it helps here or is a
  layer that earns nothing is an open question — same answer: measure first.

### 8.7 The name

The owner expects one more rename before launch. See section 9 — the *identifier* is the part
that is not cheap.

### 8.8 A teacher whose app is closed is not notified at all

Found on 2026-09-02 while making the operator screen tell the truth about delivery.

**There is no server-side notification store.** `notifyUser()` writes to whatever sockets happen
to be open, and the app keeps its own list in the phone's storage. So an in-app notification is
only ever received by somebody who is looking at the app at that exact moment. Everybody else
gets nothing — the notification does not queue and does not arrive later.

Today email covers the gap for anything important, which is why this has not bitten yet. But it
means Sikshya **cannot honestly say "we notified them in the app"** about anything, and on a
server with no mail provider configured a teacher can be approved, rejected, or have a document
turned down without ever finding out.

The fix is a notifications table the app reads on open. That is a schema change, so it needs its
own slice and a `db:push` (see the deploy-window trap in section 11). The question for the owner
is only whether it comes before launch — for a market where a cheap phone may not hold a session
open, the honest answer is probably yes.

A smaller related bug, same discovery: the "new message" email links to `/conversation/undefined`
whenever the sender is Sikshya itself rather than a person, because those notices carry no
`fromUserId`.

## 11. Traps that have already cost real time

Condensed. Each has a note in `.agents/memory/` with the full story.

### Schema and database

- **A new column on an existing table takes the site down** until `db:push` runs. The API
  auto-deploys while `db:push` is manual, and a new column on a table read with a bare
  `select()` is a 500 in that window — measured, on sign-in and registration. **A new table is
  not.** Prefer a table; split column changes across two deploys.
- **Tables get created two different ways** — `db:push` from the schema files, and hand-written
  DDL in the boot guard when Railway redeploys. Those are never in step.
  `scripts/monthly-schema/compare.sh` builds both and diffs them. Change one, change the other.
- **A column reference in a Drizzle select projection is not qualified.** In a `where` it
  renders as `"table"."id"`; in a projection it renders as a bare `"id"`, which inside a
  subquery binds to the *subquery's* row. A correlated subquery silently became
  `m.makeup_for_id = m.id` and matched nothing — no error, just every make-up class vanishing
  and a teacher suspended for misses they had put right.
- **Shifting class-days by whole days collides with itself.** Moving a month of them back
  twenty days lands some on instants their neighbours still hold. Whether it refuses depends on
  the order Postgres updates rows in, so the naive version passes several times before failing.
  Hop the whole set clear of its own range and back.

### Files and access

- **Every place a file lands needs its own answer to "who may open it?"** `GET /storage/file`
  refuses by default and allows a fixed list — uploader, agent, dispute reporter, homework
  participants, message participants, class-message participants. A new feature that stores a
  file key is refused until somebody writes its check. **The trap: the sender is always the
  uploader, so the feature looks finished to whoever built it while every recipient gets a
  403.** Test as the recipient.

### The app

- **Never set `nodeLinker: hoisted`.** Tried to shorten Windows paths and had to be reverted:
  flattening the tree collapses each package's private dependency copies, conflicts with the
  exact `@react-navigation/native` pin, and leaves React null inside expo-router — the app dies
  at startup on *both* web and native with "Invalid hook call".
- **Package versions must match Expo SDK 54.** SDK 56 packages produce a
  `ClassNotFoundException` on device, which looks like a native bug and is not.
- **A debug build installed before August 2026 will not be replaced.** The Android package was
  `com.guru.app` and is now `com.sikshya.app`; Android treats a different package as a
  different app, so a new build installs *alongside* the old one. Uninstall "Guru" first.
- **`android/` and `ios/` are generated and gitignored** — never hand-edit them. Android builds
  locally with no paid cloud account: from `artifacts/sikshya`, `pnpm exec expo prebuild -p
  android --no-install`, then `cd android && ./gradlew :app:assembleDebug`.
- **`router.back()` is a no-op** when a screen was reached without a stack entry. Use
  `router.canGoBack() ? back() : replace(...)`.
- **A bubble must be a direct child of a `flexDirection: row` container.** Wrapping it in a
  column with `alignItems` collapses it to minimum content width.
- **The board must be tested at phone width, not laptop width.**
- **Use pdf.js's legacy build**, and serve its worker as `.js` — the modern bundle needs JS old
  Android browsers lack, and a worker served as `.mjs` is refused for its MIME type.

### Tooling

- **Node's `--experimental-strip-types` cannot resolve extensionless workspace imports.** So a
  file that imports `@workspace/db` cannot be unit-tested. Pure logic lives in **import-free
  files** — `tickets.ts`, `operators.ts`, `videoCost.ts` — and gets tests; the database query
  sits beside it in a separate file.
- **A restart that silently fails makes every later test a lie.** Killing by a stale pidfile
  leaves the old server up, the new one dies on `EADDRINUSE`, and the suite goes on passing
  against an old build. Five deliberate breaks in a row reported "not caught" that way.
- **A cloud working copy can be rewound to an older commit without warning.** Commit and push
  in small increments. Never paste a file you edited before the rewind over the tree after it —
  that silently reverted `notify()` out of `messages.ts` once.
